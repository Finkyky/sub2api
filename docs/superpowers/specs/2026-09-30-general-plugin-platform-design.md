# 通用插件平台设计

日期：2026-09-30（Asia/Shanghai）
状态：根据本轮讨论整理的设计稿，待用户审阅；尚未进入实现。

## 1. 目标与定位

在 Sub2API 已有插件基础设施上扩展通用插件平台。插件用途开放，价格同步、输入敏感信息检测、输出违规或公司业务风险检查仅是验证通用能力的例子，不是平台写死的插件分类。

核心职责约定：

> 宿主决定哪个分组、什么时候调用哪个插件；插件决定是否处理、如何处理、是否拦截和允许输出什么；宿主校验并执行结果。

## 2. 已确认需求

### 2.1 开发与交付

- 开发者在本地完成开发、测试和打包，管理员上传插件安装包安装。
- 沿用现有 `.s2plugin` 包机制作为扩展基础。
- 本阶段采用安装包交付，不引入后台在线代码编辑、调试作为必需能力。
- 插件可以自定义用途、配置及内部规则，不局限于价格获取、敏感词或响应转换。

### 2.2 两种执行模式

| 模式 | 定义 | 示例 |
| --- | --- | --- |
| 独立任务模式 | 脱离业务请求，由手动或定时触发 | 上游价格探测、模型目录同步 |
| 请求链模式 | 在业务请求的指定输入或输出阶段执行 | 凭据泄露检测、输出内容风险检查 |

“独立”指独立于请求链执行，不意味着必须部署独立进程、Docker 容器或远程服务。“嵌入请求链”也不等于必须使用进程内 JavaScript 引擎。

一个插件可以同时提供两种执行能力。执行载体、开发语言及 SDK 是后续技术设计事项，不能由上述模式名称直接推导。

### 2.3 分组绑定

- 请求链插件可以绑定业务分组，只有对应分组的请求才生效。
- 业务分组不是 RBAC 用户角色。
- 未绑定该请求分组的插件不执行，也不接收该请求内容。
- 同一个插件包可以创建不同配置实例，再分别绑定不同分组。

### 2.4 插件自主决策

- 插件内部定义规则，判断是否需要处理，以及是否拦截。
- 敏感信息识别、业务风险判断、置信度、阈值及其决策逻辑属于插件及插件配置。
- 宿主不再根据检测分数重复实现一套业务判断，也不将多个插件的分数直接平均后覆盖插件决定。
- 插件可以放行原内容、处理后输出内容，或决定拦截。
- 检测插件可以仅提供检查与拦截，不必修改内容。

### 2.5 严格输出拦截

- 启用严格输出检查时，审核通过之前不向客户端发送正文内容。
- 插件决定拦截后，不向客户端返回被拦截的原始响应正文。
- 插件可以给出适合客户端的拦截说明；内部证据与客户端提示分开。
- 输入检查被拦截时，不将被拦截的请求发送给上游。

### 2.6 真实业务效果

- 插件不仅提供日志或建议，也可以通过已授权的宿主能力改变业务状态。
- 价格插件获取上游价格后，需要支持自动更新实际计费价格，不以人工确认作为必经步骤。
- 价格更新是具体业务能力，不是所有插件的统一处理流程。

## 4. 推荐的对象模型（设计建议）

### 4.1 插件包与版本

包含插件标识、版本、兼容要求、运行入口、支持的执行模式及阶段、配置定义、宿主能力声明，以及必要的 UI 和资源。

包身份、版本和内容哈希应能够追踪到具体安装内容。现有传输协议需要兼容迁移，不能通过直接修改旧协议含义让已安装插件行为改变。

### 4.2 插件实例

同一包版本可建立多个实例。每个实例保存独立的配置、规则参数、所需凭据引用和运行状态。

规则由插件解释，宿主保存与应用配置并检查配置是否合法。平台不因某个插件的内部规则增加一组硬编码业务字段。

### 4.3 分组执行绑定

把插件实例绑定到业务分组及支持的执行阶段。建议包含实例引用、分组引用、阶段、启用状态和确定性顺序。

分组选择与阶段选择是宿主配置。风险阈值、词库、公司业务规则等是插件配置；需要不同规则的分组可以使用不同实例。

管理员只能选择插件声明支持的阶段。对于需要强制执行的绑定，插件缺失、不兼容或异常不能被悄悄当作未绑定。

### 4.4 任务定义与执行记录

独立任务保存实例引用、入口、调度规则、目标范围、超时及重试配置。执行记录保存状态、耗时、结果、错误及业务变更关联。

独立任务的目标可以是渠道、账号或其他获准资源，不强迫每个后台任务绑定请求分组。

## 5. 请求链执行契约（设计建议）

### 5.1 输入阶段

```text
鉴权与基础请求解析
  → 宿主确定实际业务分组
  → 固定适用的插件、配置与执行顺序
  → 执行该组输入插件
      pass：当前内容继续
      replace：使用插件处理后的内容继续
      block：终止请求，不发送到上游
  → 最终校验及上游调用
```

分组身份来自宿主确认的上下文，不相信请求正文自行声明的分组。若路由切换实际分组，应在出站前重新确认对应绑定，避免跨分组绕过规则。

插件转换后的内容仍需满足接口结构、模型权限及路由等宿主约束；这些属于协议与授权校验，不是宿主重复执行插件的内容判断。

### 5.2 输出阶段

```text
接收上游响应
  → 宿主缓冲待返回正文
  → 上游响应完成或进入明确的异常状态
  → 执行该组输出插件
      pass：当前响应允许返回
      replace：插件输出通过宿主校验后允许返回
      block：丢弃原正文的客户端输出，只返回拦截结果
  → 宿主按客户端协议编码并发送
```

严格模式不存在“先发一部分正文，后续判断再拦截”的默认行为。

### 5.3 统一结果

| 结果 | 插件语义 | 宿主行为 |
| --- | --- | --- |
| `pass` | 不需要处理，或检查通过且内容不变 | 当前内容继续 |
| `replace` | 已处理并提供替换内容 | 校验后将替换内容交给后续步骤 |
| `block` | 插件明确决定拦截 | 终止后续链路并返回拦截结果 |

插件异常、超时和非法结果是执行错误，不是 `pass`，也不伪造为检测到违规的 `block`。

建议结果附带规则编号、规则版本、风险类别、置信度、耗时和脱敏证据。这些字段用于解释与审计；是否阻断已经由插件决定。

不要把 HTTP writer 或直接向客户端发送正文的能力交给普通检测插件，否则宿主将失去“审核前禁止输出”的统一控制。

### 5.4 多插件

首版建议按绑定顺序串行执行，使用稳定的次级排序规则解决同序号问题。

- 前一个插件输出是后一个插件输入。
- 任意插件返回 `block` 后停止，不允许后续插件覆盖放行。
- `pass` 不代表跳过后续插件。
- 不隐式合并全局、分组、账号等多层策略；分组绑定先定义清晰后再扩展其他匹配维度。

## 6. 严格响应检查的工程约束（设计建议）

### 6.1 普通与流式响应

普通响应按受控大小缓冲后检查。

SSE 等流式协议若使用严格完整检查，同样必须先缓冲完整待检查内容；检查通过后再按该协议返回，不能承诺实时首段输出。需要区分网络分块、协议事件与真正的文本内容，不能把任意 chunk 当成完整检测单元。

支持的协议、事件种类和替换结构应显式声明。对尚未支持的协议，不得静默绕过已经绑定的严格检查。

### 6.2 资源与取消

必须设计响应大小上限、最长等待时间、并发缓冲预算和客户端取消后的资源释放。

超限或超时后的行为应是明确的执行失败，不自动释放未经检查的正文。临时落盘与否、落盘保护方式及清理周期属于后续技术决策。

### 6.3 异常与失败策略

严格检查绑定建议默认失败即终止，客户端得到检查不可用的明确结果，不泄露原内容。审核模型报错、插件崩溃、输出解析失败都不能解释为低置信度或无风险。

是否提供观察模式或显式失败放行，必须作为单独配置讨论，不能成为严格模式的隐含行为。

### 6.4 用量与计费

检测内容与正式用量记录分开。输出被阻断时，上游可能已经完成计算；宿主仍要准确记录真实上游用量、插件结论及客户端是否收到内容。

被拦截请求是否收取用户费用、是否退款是产品计费规则，尚未确认，不能由任意检测插件直接改写余额或用量事实。

## 7. 独立任务与业务能力（设计建议）

```text
手动／定时触发
  → 调度器确定目标与实例版本
  → 插件执行自身逻辑
  → 插件通过宿主能力提交业务结果
  → 宿主校验授权、数据与并发版本
  → 提交变更并记录执行结果
```

任务执行不套用请求链的 `pass/replace/block`，应有独立的成功、失败和业务结果契约。若任务发现无需变更，可以成功结束并记录未产生变更。

后台任务应考虑并发限制、重复执行、重试幂等性，以及多节点部署时的调度归属，复用已有机制时需核对其适用范围。

插件可以调用的宿主能力按需声明和授权，例如限定范围的数据查询、网络访问、插件存储、渠道价格更新和事件发布。已有能力足以覆盖的用途无需为每个插件新增宿主专属逻辑；全新的核心业务操作再增加版本化接口。

### 7.1 价格同步示例

价格插件获取数据、解析并按自身配置进行映射或计算，然后调用宿主价格更新能力，校验通过后自动应用，不强制人工确认。

成本记录、渠道实际售价和倍率属于不同业务字段，接口必须明确本次更新的目标。建议保存新旧版本及来源，失败保留上一份有效价格；新请求采用新价格，已开始请求沿用其固定快照。

当前项目渠道与上游账号并非同一概念，插件的价格应用目标与认证／数据来源需要分别表达。

## 8. 管理界面建议

- 插件库：上传、安装、兼容性、版本、启停及升级。
- 插件实例：配置、规则参数、凭据引用及运行状态。
- 分组绑定：输入／输出阶段、顺序及实际生效实例。
- 独立任务：调度规则、立即执行及历史记录。
- 执行记录：请求或任务关联、规则版本、结果、耗时、错误和脱敏证据。

安装代码、修改配置、改变分组绑定、运行任务及查看敏感记录应接入已有 RBAC 与审计；具体权限目录在实现计划中细化。

## 9. 兼容演进建议

1. 保留现有 OpenAI OAuth 传输插件的契约与独占含义。
2. 引入通用请求处理与任务能力，不将旧 `Forward` 接口的语义强行扩展成所有插件入口。
3. 将现有包、实例配置和绑定迁移到兼容模型，已有插件行为保持可验证。
4. 现有内容审核以适配方式逐步接入，避免新旧系统重复检查、重复审计或互相覆盖决策。
5. 安装包格式、协议版本和数据库迁移需分别规划兼容性；不把镜像回退等同于数据库回退。

## 10. 验收场景

1. 上传合法包可安装；错误版本、错误包结构及未支持的声明被明确拒绝。
2. 未绑定组的插件完全不接收请求；绑定组按指定阶段执行。
3. 同一包的不同实例可以为不同组采用不同规则。
4. 输入返回 `block` 时，上游请求次数为零。
5. 插件可自行以置信度和规则决定 `pass` 或 `block`，宿主不二次改判。
6. 严格输出检查完成前，客户端收到的正文长度始终为零。
7. 输出返回 `block` 时，客户端不收到被拦截的原始正文。
8. `replace` 只在插件声明支持且结果通过协议校验时生效。
9. 多插件按稳定顺序执行，一旦阻断就停止后续插件。
10. 超时、崩溃、异常结果、响应超限和取消分别有可验证行为，不透传未检查正文。
11. SSE 跨事件内容可按完整语义检查，不通过单 chunk 检测假装完整审核。
12. 独立任务在没有业务请求时仍可手动／定时运行。
13. 价格任务可以自动更新实际生效的计费配置；失败不清空有效价格。
14. 在途请求不因插件升级、规则修改或价格更新而混用不同版本。
15. 日志默认不包含完整密码、私钥、认证材料或未经脱敏的内部证据。
16. 已有传输插件和既有未绑定请求行为通过兼容回归。
